# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`dockstore-support` is a sandbox of independent Java command-line tools that support the main
[dockstore](https://github.com/dockstore/dockstore) webservice: backfilling/replaying data, aggregating metrics,
generating AI topics/categories for entries, backing up tools, and testing workflow execution. It is a Maven
multi-module reactor build (`packaging=pom` at the root), Java 21, built with `./mvnw`.

Each module produces its own shaded/fat jar with its own `main()` class and its own INI-style config file — there
is no shared runtime or shared entry point. `utils` is the one module that is purely a library (no `main()`),
shared by the AI-driven modules for Dockstore API client setup, config parsing, and an AWS Bedrock/Claude
abstraction layer.

## Contribution workflow

- Branching follows **hubflow** (`feature/`, `hotfix/`, `release/` branches off `develop`/`main`), not plain
  GitHub flow.
- Never hand-edit a `pom.xml` under a `generated/` directory (e.g.
  `dockstore-support-reports/generated/src/main/resources/pom.xml`) — those are produced by the
  `flatten-maven-plugin` at build time. Make dependency/plugin changes in the root `pom.xml` or in the `pom.xml`
  at the root of the relevant submodule instead.
- For new code, prefer dependencies in this order: (1) built-in Java 21 features, (2) a third-party library
  already pulled in via Maven (check the module's and root `pom.xml`/BOM first), (3) only reach for a new
  library if neither of the above covers the need.
- When opening a PR, create it in **draft** mode — a human must explicitly mark it ready for review before it
  can be taken out of draft.
- The PR template's **Issue** field needs a link to a GitHub issue or a SEAB- ticket (e.g.
  `https://ucsc-cgl.atlassian.net/browse/SEAB-nnnn`). If one hasn't been given when drafting a PR description,
  ask the user for it rather than leaving the field blank or guessing.

## Build, lint, test

```bash
# Build everything, skip tests (fastest path to get jars in target/)
./mvnw clean install -DskipTests

# Build + unit tests for one module (from repo root)
./mvnw -pl <module> -am clean install

# Run a single test class
./mvnw -pl <module> test -Dtest=ClassName

# Run a single test method
./mvnw -pl <module> test -Dtest=ClassName#methodName

# Checkstyle runs automatically at the `compile` phase and FAILS the build on violations
# (config: checkstyle.xml, suppressions: checkstyle-suppressions.xml)
```

- `<module>` is one of: `metricsaggregator`, `githubdelivery`, `toolbackup`, `tooltester`,
  `dockstore-support-reports`, `jira_automation`, `topicgenerator`, `categorizer`, `utils`.
- Imports are auto-sorted by `impsort-maven-plugin` during the build (`process-sources` phase) — don't hand-fight
  import order.
- SpotBugs is wired in but `<skip>true</skip>` by default; it does not gate local builds.
- A full build regenerates some tracked build-artifact files — `THIRD-PARTY-LICENSES.txt` at the repo root and
  each shaded module's `<module>/dependency-reduced-pom.xml` — as an intentional side effect of the
  license-maven-plugin and maven-shade-plugin. If a build run changes these as a side effect of an unrelated
  source edit, keep the change rather than reverting it.

### Integration tests

Integration tests are `*IT.java` files run via `maven-failsafe-plugin`, and are **skipped by default** per module
via a `skip-<module>-ITs` property in the root `pom.xml` (all default to `true`). Not every module has ITs —
currently `metricsaggregator`, `toolbackup`, and `topicgenerator` do; others are unit-test only. To run a
module's ITs locally (mirrors what CI does):

```bash
./mvnw -B org.jacoco:jacoco-maven-plugin:report org.jacoco:jacoco-maven-plugin:report-aggregate \
    clean install -Dskip-<module>-ITs=false
```

Some ITs need real infrastructure (Postgres, Elasticsearch, S3-compatible endpoint, Docker) — see each module's
`README.md` and `.circleci/config.yml` (`setup_for_postgres`, `wait_for_elastic_search`, `install_dockerize`
steps) for what's expected to be running. `toolbackup`'s tests additionally expect `~/.aws/credentials` to have
a `[default]` profile (auto-generated by the test harness if missing) and a `[dockstore]` profile.

### CI

CircleCI (`.circleci/config.yml`) builds everything once (`build-all`), then runs
`metrics-aggregator-tests`, `topicgenerator-tests`, `tooltester-tests`, `toolbackup-tests` in parallel (each with
ITs enabled for just that module), then a SonarCloud scan. `categorizer`, `githubdelivery`, `jira_automation`,
and `utils` are exercised only as part of `build-all`'s unit-test run, not as dedicated IT jobs.

## Module map

| Module | Main class | Purpose | Config |
|---|---|---|---|
| `topicgenerator` | `io.dockstore.topicgenerator.client.cli.TopicGeneratorClient` | Generates AI-written topics (short descriptions) for public Dockstore entries via AWS Bedrock (Claude) and uploads them to the webservice | `./topic-generator.config` |
| `categorizer` | `io.dockstore.categorizer.client.cli.CategorizerClient` | Uses an LLM plus EDAM-style ontologies (topic/operation/input/output format & data) fetched from the [dockstore/ontology](https://github.com/dockstore/ontology) repo to categorize entries and manage Dockstore "category" collections | `./categorizer.config` |
| `metricsaggregator` | `io.dockstore.metricsaggregator.client.cli.MetricsAggregatorClient` | Aggregates workflow/tool execution metrics from S3 via AWS Athena queries and submits results (plus validation/Terra metrics) to Dockstore | INI: `[dockstore]`, `[s3]`, `[athena]` |
| `tooltester` | `io.dockstore.tooltester.client.cli.Client` | Runs Dockstore workflows through GA4GH WES (via AWS AGC/Cromwell/Toil), captures end state/runtime/CPU metrics, uploads results | `tooltesterConfig.yml` |
| `toolbackup` | `io.dockstore.toolbackup.client.cli.Client` / `Downloader` | Backs up Docker-based tools pulled from Dockstore to S3, and downloads them back down | `~/.toolbackup/config.ini` (legacy commons-configuration v1 style) |
| `githubdelivery` | `io.dockstore.githubdelivery.GithubDeliveryS3Client` | Replays GitHub webhook delivery payloads that were archived to S3 back into the Dockstore webservice | `./github-delivery.config` |
| `jira_automation` | `MilestoneChecker`, `MilestoneResolver`, `ResolutionChecker`, `SprintStart` (each has its own `main`) | Keeps GitHub issue milestones and JIRA fix-versions/sprints in sync; run individually from an IDE, not packaged as a jar | env vars only: `GITHUB_TOKEN`, `JIRA_USERNAME`, `JIRA_TOKEN` |
| `utils` | — (library) | Shared: INI config loading, Dockstore API client construction, AWS Bedrock/Claude `AIModel` abstraction, CSV I/O helpers | — |
| `dockstore-support-reports` | — | No source; aggregates JaCoCo coverage across `toolbackup`, `tooltester`, `metricsaggregator`, `topicgenerator` | — |

`topicgenerator`, `metricsaggregator`, and `categorizer` are the three modules actually shipped in the deploy
`Dockerfile` — they run as scheduled jobs against production Dockstore.

## Architecture notes

- **Every module talks to the Dockstore webservice through `io.dockstore:openapi-java-client`**, a generated
  client pinned to `${dockstore-core.version}` in the root `pom.xml` (imported via the `bom-internal` BOM). When
  the webservice API changes, bump `dockstore-core.version` here to pick up the new client.
- **Config files are INI-style**, parsed with commons-configuration2 (except `toolbackup`, which still uses the
  older commons-configuration v1 `HierarchicalINIConfiguration`), and almost universally support a `-c/--config`
  flag defaulting to a `./*.config` file in the working directory. Every module with a config file ships a
  template under `<module>/templates/`.
- **CLI parsing is JCommander-based** (`@Parameters`/commands), consistent across `topicgenerator`,
  `categorizer`, `metricsaggregator`, `tooltester`, `githubdelivery`. `jira_automation` is the outlier: no
  JCommander, no config file, plain `main()` classes meant to be run from an IDE.
- **AI-backed modules** (`topicgenerator`, `categorizer`) share the `io.dockstore.utils.ai` package in `utils`
  (`AIModel`, `AIModelFactory`, `BedrockClaudeModel`, `ClaudeModelType`) for talking to AWS Bedrock. Both default
  to invoking Claude via Bedrock and expect standard AWS credential-chain auth (see each module's README for the
  precise IAM permissions needed).
- **Fat/shaded jars**: each runnable module uses `maven-shade-plugin` to build a single executable jar
  (`target/<module>-<version>.jar`, except `toolbackup` which produces `target/client.jar` and
  `target/downloader.jar`). Run with `java -jar target/<jar> <command> [options]`.
- Untracked scratch/output directories you may see locally (`toolbackup/backup_storage/`, `toolbackup/foo/`,
  `topicgenerator/*.csv`, `metricsaggregator/*.config`) are working-directory artifacts from running these tools
  manually, not part of the source tree.
